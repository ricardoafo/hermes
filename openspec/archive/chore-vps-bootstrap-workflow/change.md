## Summary

Adds `.github/workflows/vps-bootstrap.yml` — idempotent `workflow_dispatch` + auto-on-env-change workflow that SSHes into the VPS via Tailscale and: (1) creates missing FHS dirs (`/var/log/hermes`, `/etc/hermes`), (2) renders `.env.production` from GH prod-env secrets and writes it to `/etc/hermes/env.production` (chmod 0400, owned by `hermes:hermes`), (3) mounts the Hetzner Storage Box via SSHFS when its credentials exist in the env (deferred otherwise). Unblocks #179 (CD-to-VPS deploy body). Diagnostic (#276) showed the VPS is already 80% set up — this fills the last 20%.

## Decisions

### D-1: Idempotent shell script over Ansible / Terraform

- **Decision**: plain bash script executed via `ssh bash <script`.
- **Alternatives**: (a) Ansible playbook; (b) Terraform + cloud-init; (c) systemd sysext image.
- **Rationale**: The bootstrap is ~10 shell commands. Ansible adds a control-node dependency + inventory management for one host. Terraform is for infra provisioning, not runtime configuration. sysext is over-engineered for MVP1. A shell script we can `bash -n` + `shellcheck` in CI is the smallest correct thing.
- **Cost of reversal**: LOW — Ansible-ify later if we grow to multiple VPSes.

### D-2: `.env.production` rendered from GH prod-env secrets, no template file

- **Decision**: workflow's env block enumerates `HERMES_*` secrets, script writes them line-by-line to `/etc/hermes/env.production`.
- **Alternatives**: (a) Jinja template in the repo, envsubst on the VPS; (b) `.env.production.template` committed with placeholders.
- **Rationale**: Any file-on-VPS approach either commits placeholder secrets (bad — even placeholders drift into "real" over time) or requires a separate rendering step. Line-by-line env-to-file is trivial + auditable. Secret names live in the workflow YAML (visible in review).
- **Cost of reversal**: LOW.

### D-3: Storage-box mount guarded by env-var presence

- **Decision**: the mount step runs only when `STORAGE_BOX_HOST` env is non-empty. Absent → skipped with a `WARN` note.
- **Alternatives**: (a) mount step in a separate PR; (b) fail hard when missing.
- **Rationale**: The mount and the FHS dirs are separable concerns but both belong in "bootstrap the VPS". Guarding lets this workflow ship + succeed today (Storage-box creds not yet in the env) without a second PR when creds land. Fail-hard would block the primary use case.
- **Cost of reversal**: LOW — remove the guard when creds are always expected.

### D-4: `chmod 0400` on `.env.production`, owned by `hermes:hermes`

- **Decision**: read-only for owner, no read for group / others.
- **Alternatives**: `0440` (allow group read), `0600` (allow owner write).
- **Rationale**: Contains secrets. Group access is unnecessary in the current single-user layout. Owner-write is unnecessary — the file is regenerated by re-running this workflow, not edited in place. `0400` is the tightest that still allows `hermes` runtime to read.
- **Cost of reversal**: LOW.

### D-5: Reuse the `vps-diagnose.yml` Tailscale-join scaffolding

- **Decision**: same steps (openssh install → tailnet join with userspace-networking → keyfile prep → run script). Copy-paste, not extract.
- **Alternatives**: extract to a composite action or reusable workflow.
- **Rationale**: Two callers (`vps-diagnose.yml` + this new one) — extraction is premature. When we get to a third, extract.
- **Cost of reversal**: LOW.

- **A-3.1**: After a successful run, `ssh root@hermes-01 'stat -c %a:%U:%G /etc/hermes/env.production'` returns `400:hermes:hermes`.
- **A-3.2**: The file's first line contains `HERMES_ENV=prod`.
- **A-3.3**: All non-empty `HERMES_*` secrets from the `prod` GH env appear as `KEY=VALUE` lines in the file.

### R-4: Storage-box mount succeeds when creds present, skips gracefully otherwise

- **A-4.1**: With `STORAGE_BOX_HOST` empty in the env: workflow prints a WARN line and skips the mount step; exits 0.
- **A-4.2**: With creds present: `ssh root@hermes-01 'mountpoint -q /mnt/storage-box'` returns 0 after the run.

### R-5: Zero destructive actions on missing-info paths

- **A-5.1**: The bootstrap script NEVER unmounts, deletes, or overwrites a non-empty file without diffing first. Guarded by `if [ ! -e ... ]` / `if ! grep -q ... file` predicates.

## Design

### Workflow shape

```yaml
name: VPS bootstrap
on:
  workflow_dispatch:
concurrency:
  group: vps-bootstrap
  cancel-in-progress: false
permissions:
  contents: read

jobs:
  bootstrap:
    runs-on: ${{ vars.RUNNER_LABEL && fromJSON(vars.RUNNER_LABEL) || 'ubuntu-latest' }}
    environment: prod
    timeout-minutes: 10
    env:
      # Composite-action inheritance — see #284
      ADDITIONAL_DAEMON_ARGS: --tun=userspace-networking
    steps:
      - name: Ensure openssh-client
        run: <same as vps-diagnose.yml>

      - name: Join tailnet
        uses: tailscale/github-action@v3
        with: { authkey: ${{ secrets.TAILSCALE_AUTHKEY }}, ... }

      - name: Prepare SSH keyfile
        run: <same as vps-diagnose.yml>

      - name: Bootstrap VPS
        env:
          # All the HERMES_* secrets propagated for the script to render
          HERMES_ENV: prod
          HERMES_SHADOW: 'true'
          HERMES_ALLOW_MAINNET: 'no'
          HERMES_HEALTHCHECKS__PING_URL: ${{ secrets.HERMES_HEALTHCHECKS__PING_URL }}
          HERMES_TELEGRAM__BOT_TOKEN: ${{ secrets.HERMES_TELEGRAM__BOT_TOKEN }}
          HERMES_TELEGRAM__CHAT_ID: ${{ secrets.HERMES_TELEGRAM__CHAT_ID }}
          HERMES_SLACK__BOT_TOKEN: ${{ secrets.HERMES_SLACK__BOT_TOKEN }}
          HERMES_SLACK__DEFAULT_CHANNEL: ${{ vars.HERMES_SLACK__DEFAULT_CHANNEL }}
          HERMES_SENTRY__DSN: ${{ secrets.HERMES_SENTRY__DSN }}
          HERMES_SENTRY__ENVIRONMENT: prod
          HERMES_BINANCE_MAINNET__API_KEY: ${{ secrets.HERMES_BINANCE_MAINNET__API_KEY }}
          HERMES_BINANCE_MAINNET__API_SECRET: ${{ secrets.HERMES_BINANCE_MAINNET__API_SECRET }}
          HERMES_BINANCE_TESTNET__API_KEY: ${{ secrets.HERMES_BINANCE_TESTNET__API_KEY }}
          HERMES_BINANCE_TESTNET__API_SECRET: ${{ secrets.HERMES_BINANCE_TESTNET__API_SECRET }}
          STORAGE_BOX_HOST: ${{ secrets.STORAGE_BOX_HOST }}
          STORAGE_BOX_USER: ${{ secrets.STORAGE_BOX_USER }}
          STORAGE_BOX_KEY: ${{ secrets.STORAGE_BOX_KEY }}
        run: |
          ssh -i ~/.ssh/vps_id "$VPS_SSH_USER@$VPS_SSH_HOST" bash < scripts/deploy/vps_bootstrap.sh
```

### Script shape

```bash
#!/usr/bin/env bash
# scripts/deploy/vps_bootstrap.sh
# Idempotent VPS bootstrap. Runs on the VPS via ssh bash <script.
set -euo pipefail

# 1. Ensure FHS dirs
install -d -m 0750 -o hermes -g hermes /var/log/hermes
install -d -m 0750 -o hermes -g hermes /etc/hermes

# 2. Render .env.production from env-passed HERMES_* vars
# (env vars propagated by the workflow env: block are visible via `env`)
umask 0377
{
  for var in $(env | grep -oE '^HERMES_[A-Z_][A-Z_0-9]*' | sort -u); do
    val="${!var}"
    if [ -n "$val" ]; then
      echo "$var=$val"
    fi
  done
} > /etc/hermes/env.production.tmp
mv /etc/hermes/env.production.tmp /etc/hermes/env.production
chown hermes:hermes /etc/hermes/env.production
chmod 0400 /etc/hermes/env.production

# 3. Storage-box mount (guarded)
if [ -n "${STORAGE_BOX_HOST:-}" ] && [ -n "${STORAGE_BOX_USER:-}" ] && [ -n "${STORAGE_BOX_KEY:-}" ]; then
  # ... mount steps ...
else
  echo "WARN: storage-box credentials missing — skipping mount"
fi

echo "bootstrap complete"
```

## Risks

- **R1** — Script accidentally deletes an existing `.env.production` on failure. Mitigation: `tmp` file + `mv` (atomic replace); failure before `mv` leaves the old file intact.
- **R2** — Secrets end up in workflow logs. Mitigation: GH auto-masks env values; script uses `umask 0377` before write; no `set -x`.
- **R3** — Storage-box mount fails mid-flight (bad key), leaves an orphan mount point. Mitigation: `mount | grep -q /mnt/storage-box` check before mounting; refuse if already mounted with different source.
