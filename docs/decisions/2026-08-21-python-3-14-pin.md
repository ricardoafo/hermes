# Python runtime pinned to 3.14 (latest stable)

**Date**: 2026-08-21
**Author**: Maintainer
**Related**: ADR-003 §User Interface (partially superseded by this entry), ADR-010 §Package manager, `openspec/archive/phase-0-python-toolchain/`

## Decision

Pin the Python runtime to 3.14. `pyproject.toml` declares
`requires-python = ">=3.14,<3.15"`. `.python-version` file reads `3.14`.

## Context

ADR-003 README §64 says "Python 3.11+" and §07 (`user-interface.md`)
says "Python 3.11 via uv". Both were written when 3.11 was the current
stable. The Phase 0 venv was already recreated at 3.14 during dev-env
setup (2026-08-21 morning) — the ADR wording never caught up.

The `phase-0-python-toolchain` SDD exploration reflected this drift
and initially recommended "revert to 3.13" to match the older ADR text
plus a stale engram note (`sdd-init/hermes` — targets 3.13.15). That
recommendation was rejected on the grounds that:

- 3.14 is the current stable — one full release ahead of 3.13
- The venv is already 3.14; no dep has hit an incompatibility during
  local testing to date
- No downstream integration constraints (VPS runs whatever `uv python
  install` gives it; CI pulls Python via `astral-sh/setup-uv`)
- Staying on 3.14 buys ~12 additional months of upstream security-fix
  window vs pinning back to 3.13
- The narrower `>=3.14,<3.15` pin (vs `>=3.13`) prevents accidental
  drift into 3.15 on next `uv resolve`

## Alternatives considered

**Pin to 3.13.15** (the "revert to what ADRs say" option):

- Matches existing ADR-003 wording verbatim
- Loses ~12 months of security-support horizon
- Requires recreating the venv (delete + `uv python install 3.13` +
  `uv venv --python 3.13`)
- No functional benefit for hermes' current scope
- Rejected

**Unpin upper bound** (`requires-python = ">=3.14"`):

- Would auto-adopt 3.15 the moment it lands and a `uv resolve` runs
- Loses the "pinned known-good runtime" discipline
- Rejected — the whole point of the pin is deterministic environments

**Pin to 3.14 exactly** (`requires-python = "==3.14.*"`):

- Rejected — semantically equivalent to `>=3.14,<3.15` but less
  idiomatic in pyproject.toml conventions

## Rationale

Latest stable + narrow upper bound is the standard uv-project pattern
and matches how the rest of the toolchain versions are pinned
(compatible-release specifiers in `pyproject.toml`, exact versions in
`uv.lock`). The pattern is: `pyproject.toml` says "any 3.14.x",
`uv.lock` says "3.14.N-specific", CI reproduces from the lock.

## Consequences

**What this locks in**:

- Python 3.14 as the runtime for dev, CI, and VPS deployment
- All tool configs target 3.14: ruff `target-version = "py314"`,
  mypy `python_version = "3.14"`
- `astral-sh/setup-uv` in CI resolves 3.14 automatically via `uv sync
  --frozen` (which enforces `.python-version` + `requires-python`)

**What this forecloses**:

- Deployment to a host with Python < 3.14 pre-installed. Not a
  concern — the VPS gets Python via `uv python install`, not the
  system package manager
- Any dependency that lacks a 3.14 wheel. Most first-party libraries
  publish 3.14 wheels by now, but long-tail C-extension libs may lag.
  If more than 2-3 deps hit this at Phase 1, revisit the pin

**What we'll revisit**:

- When 3.15 lands as stable (roughly Oct 2027), evaluate whether to
  bump. Default: yes, unless a dep is stuck on 3.14 or a runtime
  behavior change breaks us
- If a critical dep never ships a 3.14 wheel and can't be replaced,
  regress to 3.13 with a new journal entry
