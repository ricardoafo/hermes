# Prose Style Guide — Comments, Docstrings, Docs, Free Text

**Type**: Guide (living document — PR any change)
**Owners**: Ricardo Afonso (sole reviewer)
**Applies to**: everything with words in this repo — code comments,
docstrings, ADRs, guides, decisions, runbook, research digests, PR bodies,
issue bodies, commit messages, workflow / job / script names.
**Description**: Comments, docstrings, docs, PR/issue bodies — banned words, formatting rules, per-artifact style.

Prose in hermes has one job: **let a future reader answer their question
faster than reading the code would**. Every rule here serves that. When a
rule would slow the reader down without adding certainty, break it and
document why in the PR body.

## Golden rules

1. **Comments explain WHY, docstrings explain WHAT.** The code is the
   what. If the WHY is obvious from the surrounding code, don't add a
   comment. If the WHY involves a hidden constraint, subtle invariant,
   or non-obvious tradeoff, write it. Per ADR-009 §5.
2. **Measurement over assertion.** State what was verified with a number
   or artifact ("`pytest tests/ -q` — 47 passed in 2.3s"), not what was
   attempted ("comprehensive test suite"). One stale number breaks
   reader trust for the entire document; keep numbers reproducible or
   don't cite them.
3. **Docs move with code.** A change making a doc false includes the doc
   fix in the same commit. Stale docs are defects, not backlog items.
4. **No emoji anywhere in the repo.** Words are diffable, grep-able,
   consistent across terminals; emoji are multi-codepoint sequences that
   split in diffs, render inconsistently, and are noise. Exceptions:
   quoted product output (preserve evidence), user-facing runtime
   messages (Telegram, CLI output to humans).
5. **Zero footprint of external / unrelated projects** — see
   [dev-workflow.md §Zero-footprint policy](dev-workflow.md#zero-footprint-policy).
   Repeat here because it applies to every artifact this guide governs.

## By artifact type

### Python comments

- **No WHAT-comments.** `x += 1  # increment x` gets a code-review request
  to delete. Well-named identifiers already say what.
- **WHY-comments start with the hidden constraint.** Format:
  `# <reason>: <consequence>`. Example:

    ```python
    # Binance rate-limits weight/min not requests/min; batch price
    # fetches into single-symbol requests to stay under 6000/min.
    prices = [client.get_price(sym) for sym in symbols]
    ```

- **`TODO:` comments include an issue number.** `# TODO(#42): retry on 5xx`
  not `# TODO: retry later`. Comments without expiry rot.
- **Never AI attribution in comments.** No `# Generated by ...`.
- **Warnings are multi-part decisions.** Format: `WARNING: <what> — <why> —
  <what to do instead>`. Never a bare `WARNING:` without the why-and-what.

### Python docstrings (Google style, per ADR-009)

- **All public API has a docstring.** Enforced by ruff's `D` family
  (D100/101/102/103 for module / class / function / method public
  interface).
- **Structure**:

    ```python
    def compute_next_lot(lots: list[Lot], quantity: Decimal) -> Lot:
        """Pick the next lot to consume under FIFO discipline.

        Chooses the oldest lot with `qty_remaining >= quantity`. If no
        single lot has sufficient quantity, splits across the oldest N
        lots that together cover the quantity.

        Args:
            lots: All open lots for the coin, in any order. Function
                sorts internally.
            quantity: The quantity being sold, denominated in the coin's
                base unit.

        Returns:
            The lot that should be consumed (or the first of N lots
            being split).

        Raises:
            InsufficientInventoryError: Sum of `qty_remaining` across
                `lots` is less than `quantity`.

        See Also:
            ADR-002 §FIFO for the tax rationale; ADR-003 §03 for the
            persistence schema this operates on.
        """
    ```

- **Imperative mood on the summary line.** "Pick the next lot" not
  "Picks the next lot". Same rule as commit messages.
- **`Raises:` is mandatory when the function raises.** Silent failures
  are always at least SEV-2.
- **`See Also:` links to ADRs, decisions, invariants** — do not
  paraphrase them.

### Test docstrings

- **Every test cites what it proves.** Format:

    ```python
    def test_fifo_picks_oldest_first_when_all_have_sufficient_qty():
        """FIFO invariant I-04: given N lots with qty_remaining >= sale,
        consume the oldest by created_at.

        Motivation: ADR-002 requires deterministic FIFO for Spanish
        tax-lot accounting. Wrong ordering produces wrong Modelo 100
        declaration (F1 severity).
        """
    ```

- **SEV-1 test paths carry the rubric annotation** above the test
  function:

    ```python
    # SEV-1: Security axis S2 (tenant-isolation IDOR)
    def test_position_query_never_returns_other_tenant_data(): ...
    ```

    Enforced by the `sev1_guard` pytest plugin (lands Phase 0 per ADR-007).

### ADRs

Immutable once Accepted (per AGENTS.md prohibition #10 — editorial
scrubs excepted). Style rules:

- **Structure** per ADR-009 template (Status, Deciders, Context,
  Decision, Consequences, Cross-references).
- **Decision paragraph in one sentence.** Everything else is
  supporting.
- **Cite regulations by their identifier** (`DGT V2232-25`, `LOPDGDD`,
  `RD 1457/1986`) not by paraphrase.
- **Mermaid diagrams mandatory** for anything describing flow,
  architecture, or data shape. A prose-only ADR that would be clearer
  with a diagram is a review finding.
- **Rejected alternatives get their own section**, each with the
  argument for + why we passed. Deleting the alternatives from history
  loses the reasoning.

### Guides (this doc's category)

- **Second person imperative** ("Run the following", "Verify that the
  output matches"). Not "We run", not "One should run".
- **Every command block is copy-pasteable and tested.** If a command
  needs edits before running, mark the substitutions explicitly:

    ```bash
    gh pr create --title "<your-conventional-commits-title>"
    ```

    Not `gh pr create --title MY_TITLE_HERE`.
- **Rationale sections at the end**, not woven into the procedure.
  Reader wants to do the thing first; reasoning comes if they want it.

### Decisions journal (`docs/decisions/`)

- **Filename**: `YYYY-MM-DD-short-slug.md`.
- **Body**: Decision (one sentence), Context (why now), Consequences (what
  it locks in, what it forecloses, what we'll revisit).
- **Never edit a merged entry.** Supersede with a new dated entry that
  references the old.

### Runbook (`docs/runbook/`)

- **Symptom → Diagnosis → Recovery → Post-incident → Prevention** —
  same shape every entry, per ADR-009 §5.
- **Copy-paste commands, no prose between recovery steps.** Prose belongs
  in Post-incident.
- **Last-exercised date at the top.** Runbook entries older than a year
  without exercise are flagged for review.

### Research (`docs/research/`)

- **External citations mandatory.** URLs, doc IDs, section numbers.
  Distinguish confirmed facts from working hypotheses explicitly.
- **What this closes / what this opens** sections. A research digest
  without a resolved question is a note, not research.

### Commit messages

- Conventional Commits format (per [dev-workflow.md §Commit convention](dev-workflow.md#commit-convention)).
- **Body wraps at 72 chars, explains WHY.** The diff is the WHAT.
- **Reference issues in the footer**: `Closes #42`, `Refs #17`. Never
  in the subject line.
- **No AI attribution.** Global rule.

### PR bodies

Use the template in `.github/pull_request_template.md`. Rules from that
template:

- **Summary** explains WHY the change is being made, not what changed
  (the diff is the what).
- **Testing** cites measurements, not assertions.
- **Risk** is honest about blast radius.
- **Follow-ups** prevent scope creep.

### Issue bodies

Use the templates in `.github/ISSUE_TEMPLATE/`. Bug template captures
observed / expected / why / where / silent-failure — every field
matters. `bug-triager` agent uses these fields to assign severity per
rubric.

## Anti-patterns — banned words and phrases

The following are AI-voice signals. Reject in review.

| Word / phrase | Why banned | Preferred |
| --- | --- | --- |
| `comprehensive` | Signals "vibes-tested", not "I ran and counted N tests" | Cite the number: "47 tests across FIFO cases" |
| `robust` | Reader has no idea what was made robust | Describe the failure mode you prevented |
| `elegant` | Aesthetic judgment, unfalsifiable | Delete or replace with the concrete tradeoff |
| `leverages` | Bloat verb for "uses" | `uses` |
| `utilize` | Bloat verb for "uses" | `uses` |
| `seamlessly` | Implies no observable seam, always misleading | Describe what's actually observable |
| `powerful` | Empty adjective | Delete or describe the specific capability |
| `simply` | Reader who doesn't find it simple feels stupid | Delete |
| `just` (dismissive) | Same as `simply` | Delete |
| `obvious` / `obviously` | Same as `simply` | Delete; if it were obvious you wouldn't be writing this |
| `should work` (in docs) | Uncertain — either verified or don't ship | Verify then say "does work" with the evidence |
| `we will add later` | Deferred work without an issue rots | Open an issue, reference it |
| `TBD` / `TODO` (without context) | Uncontexted TODOs rot | `TODO(#N):` with issue, or delete |
| `here` (as link text) | "Click here" is bad a11y and scan-hostile | Descriptive link text ("see the ADR-002 tax posture") |

Also banned:

- **Multi-adjective stacks**: "clean, concise, elegant, robust" — pick one
  concrete claim.
- **Vague quantifiers**: "many", "several", "a lot of", "some" — cite
  numbers or delete.
- **Passive voice for actions with agents**: "The migration was applied"
  loses who applied it → "The migration runner applies migrations at
  startup".
- **Pronouns without antecedent**: "This makes the query faster" — this
  what?

## Formatting rules

- **Tables when comparing 2+ items with the same attributes.** Prose
  otherwise. A three-row bullet list should have been a table.
- **Numbered lists for ordered procedures.** Bullets for unordered facts.
- **Code blocks always have a language tag** (` ```bash `, ` ```python `,
  ` ```text ` for output). Enables syntax highlighting and lint checks.
- **Links use descriptive text.** Not `[here](url)`, not `[link](url)`.
- **Headings use sentence case**, not Title Case. "How to add a guide",
  not "How To Add A Guide".
- **One blank line between paragraphs.** Never two.
- **Wrap Markdown at 80 chars** for readability in `git diff`. Code
  blocks and tables exempt.
- **Every Markdown file ends with a single trailing newline.** Enforced
  by pre-commit `end-of-file-fixer`.

## Diagrams

- **Mermaid, embedded in the doc**, not external image files. Images
  bit-rot; Mermaid stays diff-able and version-controlled.
- **One diagram per concept.** A 40-node diagram is a symptom of
  needing more docs, not a better diagram.
- **Direction chosen deliberately**: `TB` (top-to-bottom) for
  hierarchies, `LR` for pipelines / flows.
- **Node labels are noun phrases**, not sentences. Long text goes in
  the surrounding prose.

## Language and voice

- **English throughout the repo.** Ricardo speaks Spanish natively but
  the repo language is English (per ADR-009 §Language). Rationale:
  future collaborator ceiling, tooling assumptions (linters, AI
  reviewers), and consistency with dependency ecosystems.
- **Second person imperative in guides** ("Run the tests"). Third
  person in ADRs and runbook ("The rebalancer runs hourly", "Operator
  runs `restic snapshots`"). First person plural ("we") only in the
  Rationale sections of ADRs where a collective decision is
  explicitly being described.
- **Present tense for what the code does.** Past tense only for what
  already happened (changelog entries about past releases, incident
  post-mortems).
- **Active voice unless the actor is genuinely irrelevant.** "The
  runner picks the oldest candidate" not "The oldest candidate is
  picked by the runner".

## Enforcement

Some rules are enforced by tooling; most are enforced by review.

| Rule | Enforced by |
| --- | --- |
| No emoji in text | (planned) pre-commit hook grepping for emoji ranges |
| Line length in Markdown | Not enforced (readability > strict wrap) |
| Code block language tags | markdownlint MD040 (already on) |
| Descriptive link text | markdownlint MD059 (not currently on — evaluate) |
| Trailing newline | pre-commit `end-of-file-fixer` (already on) |
| Public API docstrings | ruff `D` family (lands Phase 0) |
| No `# noqa` without reason | ruff config + review |
| No stale docs | Review + occasional grep audits |
| Everything else here | Review |

When a rule is broken and a reviewer asks for a fix, cite the section of
this file in the review comment. When the rule itself is the problem,
open a PR to change this file.
